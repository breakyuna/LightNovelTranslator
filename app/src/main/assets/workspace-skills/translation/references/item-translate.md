# `items` 翻译

为工程内的 `item` 翻译、补译、续做或重译，形成完整译文。适用 TXT、EPUB 及其他导入为条目的文本；PDF 页流程已冻结，本参考不处理页面。

## 目标与范围

用 `project_summary` 读取工程语言、资产顺序、修订和条目总数，用 `project_statistics` 读取状态计数。结合用户请求判断翻译目标：

- 明确要求翻译且未限定范围时，以当前待译内容为目标。
- 补译按指定的遗漏范围定位，重译按指定对象及允许替换的内容定位。
- 续做结合最新状态、已有实际结果和对话中的工作记录恢复剩余目标。

用 `list_items` 按资产和条目顺序分页，记录 `item_id`、`asset_id`、`slot`、`row`、`status` 和 `fingerprint`。将用户指定的文件、条目、状态、文本条件和排除项解析为实际目标，以稳定的 `item_id` 去重；正文与姓名属于同一对象。

按文件与条目顺序组织目标，把共享语境、跨条目表达或指代关系紧密的目标放在一起判断。当前工具没有独立的 `warnings` 数据集；不要编造警告列表，也不要声称存在 `ws.contract`、`batch_item_translation` 或 `queryItemContexts`。

## 读取与语境

对每个目标调用：

```
read_item {"item_id":12345}
```

返回的 `source`、`translation`、`status`、`fingerprint` 和 `asset_id` 是当前事实。需要邻近条目时，用 `list_items` 的 `after_id` 向前后分页，按返回顺序选择相邻 `item_id`，再逐个 `read_item`；不要假设相邻 ID 一定连续或一定属于同一章节。

姓名、称谓、固定译名和重复表达用 `search_items` 定位：

```
search_items {"text":"称呼或术语","limit":20}
```

搜索结果只提供命中条目，不提供完整上下文；对命中条目再 `read_item` 阅读邻近文本。术语约束从 `project_text_policy` 的 `TERM` 规则读取，结合 `target`、`note`、`scope` 和大小写条件判断适用性。

`read_workspace_material` 可读取严格 UTF-8 的原稿文本材料；打包 EPUB 是二进制，不能据此读取内部章节。EPUB 工程以导入后的 `item` 为目标，结构阅读按 `epub` 技能。

## 形成译文

按业务单元读取原文、现有译文、姓名和必要语境。缺少参与者、指代或剧情事实时，用相邻条目和 `search_items` 补充；仍无法确定时，检查能否忠实保留原文歧义，或按证据确定译法的适用条件。

形成正文与姓名的完整译文，同时遵守条目约束：

- 每条原文对应本条完整译文，保留条目边界、顺序、行数和换行。结合跨条目语境理解内容，按用户明确要求处理结构变化。
- 控制符、占位符、标签、转义与保护结构保持位置和边界。引号、括号可以转换为同类目标语言形式；原文半边或跨条目延续结构仍需保留。
- 需要提交姓名译文时，用 `prepare_item_changes` 的 `name_source`/`name_translation` 数组表达；正文中的称谓、头衔、敬称和解释留在对应正文位置。`read_item` 不返回独立姓名数组，姓名证据从正文、`search_items` 和可读取的原稿材料取得。
- 失败条目的重试沿用用户已明确的决定。尚无决定时，说明数量并询问处理或跳过；不要静默丢弃。

保存每个目标的当前结论和完整新值。对未决对象，说明缺失事实、已完成的补查、已尝试的译法和继续条件。

逐项核对当前单元的含义、结构、关系、术语和表达质量。默认提交本单元并核对回执，再进入下一单元；统一提交时，先保存方案再处理下一单元。

## 提交变更

`prepare_item_changes` 的 `changes` 参数接受完整变更 JSON：

```json
{"items":[{"item_id":12345,"fingerprint":"当前64位sha256","translation":"完整译文","status":"PROCESSED","name_source":["原文姓名"],"name_translation":["译文姓名"]}]}
```

- 每个目标必须使用 `read_item` 返回的当前 `fingerprint`；指纹过期时整个提案按冲突策略失败。
- 未指定字段保持原值。翻译修改默认 `PROCESSED`；可使用 `NONE`、`PROCESSED` 或 `EXCLUDED` 表达明确状态。
- 一次最多 1024 个不同条目；不要截断请求范围。`policy` 可为 `REJECT_BATCH`（默认）或 `ACCEPT_INDEPENDENT_OBJECTS`。
- 提案只进入待审批存储，不直接写工程。用户可接受子集。
- 提交后调用 `item_proposal_status`，核对实际已提交、被拒绝的条目和回执修订。没有回执时不得声称已保存，也不得声称批量工具 `batch_item_translation` 存在。

## 关联问题与后续处理

根据本次翻译、语境读取和结果核对中发现的线索，记录并执行关联检查：

- 后文确认了姓名或关系时，核验已使用该译名或指代的目标。
- 发现结构损坏或命题错配时，补查相同条件下的相关表达。
- 发现可靠译法时，检查同系列表达和人物声音的一致性，并按语境与阶段确认适用性。

新证据改变身份、译法、结构、待写入值或未决结论时，重新 `read_item` 取当前指纹，核验本次范围内受影响的正文与姓名。原问题修正后，继续完成已产生的后续检查。等价问题合并，有效证据复用，只重查变化影响的部分。

发生写入后，按 `item_proposal_status` 核对真实成功对象、译文和字段副作用，处理回执指出的失败。写入后发现的问题同样进入关联处理，修改已有结果时使用最新事实和指纹。

## 完成检查与交付

结束前对照完整目标及问题记录，逐项确认：

- 每个目标均有实际结果或明确的未决说明。
- 待写入方案完整且通过检查，所有指纹来自最新 `read_item`。
- 提案回执已核对，未把待审批项说成已保存。
- 已发现的关联影响均有当前核验结果。

发现可执行的剩余工作时继续处理。未决事项说明决定性缺失事实、已完成的补查和继续条件。

说明覆盖了哪些条目、实际判断了哪些内容，以及执行方式、完成结果和剩余工作。按 `item_id` 去重，核对已完成、已排除和剩余目标是否覆盖用户要求的范围。

说明正文修改数、姓名修改数和待审批数量各自的统计方法，将同一条目的多个问题关联起来展示。注明方案、单次提案统计与工程累计进度各自表示的内容。
