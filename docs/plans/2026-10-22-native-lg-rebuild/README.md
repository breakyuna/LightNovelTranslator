## 2. 用户决定与规则适用

1. 产品中心从 `Book / Edition` 转为 `Project / Asset / Item / PDFPage / AgentChat`。
2. 新首页为工程入口；打开工程默认进入 Agent，工作台和校对是平等的业务入口。
3. 旧书架、阅读历史、阅读器、Apple 风格组件、章节/Edition 业务和小说专属翻译引擎不作为新产品必须保留的功能或实现。
4. LNT 唯一运行时保留范围是 `core/agent/koog/` 中的 Koog 接入框架，具体边界见第 5 节。其他旧业务实现不按“可复用”理由继续进入新主链路。
5. 对 LG 的对齐是业务行为、能力和交付结果对齐；Android 导航、文件选择、后台执行和通知采用原生机制。
6. 原生工程统一使用 `.lnt`，保留版本升级和备份恢复。用户于 2026-10-24 取消 `.lg` 工程导入/导出、双向回灌及 Pi 会话历史转换；这些能力不再设计、实现或验收。LG 仍是业务功能参照，不要求工程文件或 Agent 框架互通。
7. 初始规划轮只授权深入分析、计划文档及根规则同步。用户随后已要求开始并持续修改，实施进度以 HANDOFF 为准；不自动授权提交、推送、触发 CI、真实付费调用或发布。旧用户数据仍不得直接删除。

当前 `AGENTS.md` 已按用户追加指令同步取消书中心定位、固定书架导航和沿用旧 UI 等冲突约束，并指向本计划。保留本机禁止 Gradle、凭据保护、验证真实性及无关改动保护等仍适用约束；原有未提交修改不回退。正式实施的第一项任务继续核对规则适用性，并同步用户说明。

“仅保留 Koog”约束产品运行时代码，不要求删除 Git 历史、签名身份、Gradle wrapper、现有 CI 入口及用户数据。构建依赖也按新调用链整理；旧小说测试不作为新工程行为的权威。

## 4. 完整对齐的定义

最终版本必须覆盖：

- `.lnt` 工程创建、打开、保存、资产导入、复制、设置对齐、修订、重置和备份恢复。
- LG 的 Agent 对话、编辑/分支、输入队列、执行中引导、停止/继续、压缩、用量、材料与产物。
- 可编程工作区、变更预览与提交、用户问题、手动/自动审批、技能、人格、联网搜索和网页获取。
- 批量翻译、模型能力、调度、密钥池、重试、恢复、文本处理和全部配置。
- 术语、文本保护、译前/译后替换、自定义提示词、预设、导入导出、统计和完整校对台。
- TXT、Markdown、EPUB、PDF、字幕、JSON、表格、RenPy、TRANS、RPG Maker MV/MZ 与 RGSS 的导入和正确写回。
- 原生手机/平板界面、文件与文件夹交付、日志、诊断、存储和升级。旧 LNT 数据迁移已按用户决定移出当前范围，不列为交付要求。

阶段版本可以先交付部分闭环，但不得标为“完整 LG 原生版”。RGSS、PDF、OAuth、工作区或技能缺失都属于尚未完成，不因困难而悄悄移出范围。LG Termux 尚缺的验收证据也不能当成本计划跳过验证的依据。

不要求复制 Electron 窗口、浏览器启动凭据、HTTP/SSE、终端命令、桌面自动更新程序或在 Android 上启动 Windows 游戏。这些是原平台的载体；相应业务入口、访问边界、恢复和文件结果必须有原生等价实现。普通内容阅读只作为工作区/原稿预览，不另建旧小说阅读平台。

## 6. 架构决定

1. 全部业务 UI 使用 Compose，不使用 WebView 承载主界面，不运行 Node 业务后端。
2. 工程事实和应用运行记录分开：原生 `.lnt` 项目存储由专用 SQLite 适配器拥有，独立管理 schema 版本与迁移；Room 管理应用索引、任务、审批与 Koog 运行记录。
3. 界面、Agent、翻译、导出共用新应用服务和唯一工程写入口。
4. 任务由应用运行时与前台 Service 管理，页面 ViewModel 只订阅与提交命令。
5. 保留可编程工作区；嵌入脚本引擎和原生能力桥是必做子系统。QuickJS 是首个候选，不是已经验证的最终选择。
6. LG 的动态技能、说明和预装脚本按新执行环境迁移；不能直接复制仍声明 Node/npm 能力的指令。
7. `.lnt` 原生保存/重开、版本升级、Koog 历史与备份恢复分别验收；外部工程/会话兼容及旧 LNT 数据迁移不适用。
8. 首轮以单一活动工程、单一活动 Agent 回合对齐 LG；不额外引入多 Agent 编队或云端后端。

## 7. 先验证的高风险问题

| 门槛 | 要回答的问题 | 未通过时的处理 |

门槛产物进入新工程并可继续使用，避免只做不可复用的演示。门槛分为技术可行性、正式实现和跨模块集成三层，开工依赖与完整验收条件见 [实施计划](IMPLEMENTATION_PLAN.md) §4.1。基础 TXT 闭环和四页面原型可在其直接依赖验证后推进，不等待无关复杂格式；批量推广 UI/格式之前必须验证对应技术路径。G1—G5 和全部功能仍是完整版本的退出条件，局部通过不代表 M1 或产品完成。

早期交付先验证“TXT 工程 → 手动翻译 → 校对 → 保存 → 重开”，再接“Agent 读取 → 固定差异审批 → 一次提交 → 重启核对”。使用真实本地存储与应用服务、假模型；不因此授权真实付费请求。迁移字段样本提前参与领域模型设计，最终迁移与旧实现退役仍按后期门槛执行。

## 8. 完成标准与交付责任

所有功能 ID 都有“实现入口 → 自动化行为证据 → 必要真机/视觉证据 → 交付产物”。每种格式都有原始文件、翻译/修改、导出、再次读取的闭环；工程回灌还要核对资产、修订和历史。

必须完成旧主链路删除、资源说明同步、数据迁移、升级验证和签名包验证，不能永久保留两个产品主链路。先保护并迁移旧数据，再清理实现；本次计划不授权删除任何用户数据。

本机只做静态核对。Gradle、测试、Lint、APK 与设备验证在 PC/已获授权的 CI/设备环境执行。后续真实模型调用、外部发布按会话授权执行，普通回归默认使用假模型和自有夹具。

如遇新的不兼容，先定位功能 ID 与影响，再调整设计和任务；不能通过隐藏入口、硬编码成功、跳过测试、冻结所有复杂格式或改变完成口径获得“完成”。
